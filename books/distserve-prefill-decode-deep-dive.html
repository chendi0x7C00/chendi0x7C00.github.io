01 / Problem

不是 GPU 不够快，而是两种任务互相拖慢。

continuous batching 把 prefill 与 decode 放在一起以提高 tokens/s；一旦加上 TTFT、TPOT 双 SLO，这个选择同时制造执行干扰、排队干扰和资源配置耦合。

PREFILL · TTFT

一次并行处理整段 prompt

输入 token 可同时计算；prompt 不短时通常趋向 compute-bound。对 13B 模型，单条 512-token 输入已接近让一张 A100 算力饱和。它产出第一个 token 与后续所需的 KV cache。

Compute较长序列更容易受算力限制
小 batch超过饱和阈值后继续堆批只会拉长等待

论文 §2.1、§3.1、Figure 3(a)

DECODE · TPOT

每步只为每个活跃请求前进一个 token

单步计算量小，却仍要搬运模型权重与中间状态，因此通常受 HBM 带宽限制。增大 decode batch 能摊薄权重读取，提高利用率，但 batch 又受 KV cache 显存与 TPOT 约束。

Bandwidth小 batch 时常受显存带宽限制
大 batch通过批处理提高每 GPU goodput

论文 §2.1、§3.2、Figure 3(b)

分水岭：从“共享一次执行”改为“分开优化两个阶段”

  • Orca / vLLMcolocated continuous batching 提高整体吞吐，但一个长 prefill 会拖慢同批 decode；反之 decode 也会挤占 prefill。
  • SARATHI / MIIchunked-prefill + piggyback 缩短单次干扰，却不能消除干扰；历史 chunk 的 KV cache 还会被反复读取。
  • 简单拆开调度不混批但在同一 GPU 上串行执行，仍互相排队；优先任一阶段都会伤害另一阶段的延迟。
  • DistServe物理拆分实例与权重副本，独立选择 GPU 数、TP／PP 与 batch；代价是 KV 传输和更复杂的放置。

论文 §2.2–§2.3、§8；相关系统名称均为论文中的比较对象。

工程师视角

这里真正被拆开的是“干扰域”和“配置域”，不只是两个函数调用。若只把 prefill／decode 写成两个服务，却仍共用同一 GPU 时间片和同一并行策略，论文指出的核心问题并没有消失。

▶ 跑一遍 · Figure 1 的 3-GPU 理想配置

论文设定：13B 模型、输入 512、输出 64、80 GB A100；90% SLO attainment。以下全部采用 Figure 1 与 §1 的数值。

  1. 现有 colocated 系统：单 GPU goodput 约 1.6 req/s。
  2. 独立测量阶段能力：prefill-only 5.6 req/s，decode-only 10 req/s。
  3. 理想地配 2 张 prefill GPU + 1 张 decode GPU：整体速率受 decode 侧限制，为 10 req/s。
  4. 每 GPU goodput = 10 / (2 + 1) ≈ 3.3 req/s/GPU。
  5. 相对提升 = 3.3 / 1.6 ≈ 2.1×。

注意：这是论文用 phase-only 曲线做的理想化分配演算，不是该 3-GPU 配置的端到端实测点。

02 / Architecture

两池算力，一条 KV 通道，一个全局规划器。

HIGH NODE-AFFINITY

跨节点带宽充足：两阶段独立搜，再复制

分别枚举 prefill 与 decode 的可行 TP／PP，模拟并用二分搜索找满足 attainment 的最大速率，最后按目标流量复制。算法复杂度 O(NM²)，论文报告最大设置求解低于 1.3 分钟。

L ≈ 2.5 + (200.3 − 1) × 0.15 = 32.40 s

意义：即使只关心交互体验，也不能只报一个“平均延迟”。长输出会放大 TPOT，长 prompt 会放大 TTFT；两个预算需要分别 attainable。

05 / Design decisions

真正值得学的，是六次有代价的选择。

每张卡都按同一顺序拆解：问题、被否决的方案、选择理由、必须支付的代价。论文结论与工程解读分开写，避免把“有效”读成“免费”。

D1

物理拆分 prefill 与 decode

先拆干扰域，再谈调度优化。

决策问题
两阶段共享 GPU 时，执行与排队互相干扰，怎样同时守 TTFT 与 TPOT？
被否决方案
Orca／vLLM 的 colocated continuous batching；SARATHI／DeepSpeed-MII 的 chunked-prefill + piggyback；同 GPU 串行或优先级调度。
为什么这样选
不同 GPU 池从机制上移除跨阶段执行干扰，也解除 GPU 数与 TP／PP 配置的绑定，让每阶段只对自己的延迟目标负责。
代价／权衡
两份权重、KV cache 跨实例传输、更多部署组件；实例间依赖还会引入故障传播路径。
D2

把目标函数改成 per-GPU goodput

先定义“合格请求”，再最大化速率。

决策问题
原始 tokens/s 很高的系统，可能仍让大量请求错过延迟目标，成本指标该写什么？
被否决方案
以 Orca／vLLM 式整体吞吐为唯一目标；或只优化平均延迟，而不显式给定 SLO attainment。
为什么这样选
goodput 直接写成“达到 attainment 目标时，每张 GPU 能承接的最大请求率”，与服务质量和 GPU 成本同时相关。
代价／权衡
必须提供 TTFT、TPOT 与 attainment 目标；结果依赖负载分布。离线、延迟不敏感场景反而可能更适合高吞吐混批。
D3

两阶段采用不同 batch 与并行策略

执行时间和排队时间要一起算。

决策问题
compute-bound prefill 与 bandwidth-bound decode，为什么不该共用同一并行配置？
被否决方案
vLLM 式的 colocated 共享并行设置；或只看单次执行加速、忽略到达率升高后的排队项。
为什么这样选
Prefill 小 batch 靠近饱和长度 Lm；decode 靠大 batch 提升利用率。低到达率／紧延迟偏好 intra-op，高到达率的排队项增大后 inter-op 更有利。
代价／权衡
需要 profiling 与搜索；非均匀 prompt 会造成 pipeline bubble，intra-op 通信也使加速比 K 小于理想值。
D4

让物理放置服从 KV 的层间拓扑

网络不是事后才看的部署细节。

决策问题
跨节点只有有限带宽时，怎样避免解耦后的 KV 传输吃掉收益？
被否决方案
不做拓扑约束的任意跨节点放置；或始终把完整 prefill／decode instance 对放同机。论文中的 DistServe-High 也不适用于低跨节点带宽物理集群。
为什么这样选
KV 只在对应 layer 间流动。按 inter-op stage 切分 instance segment，再把同阶段 P／D 片段同机放置，就能强制走节点内 NVLINK。
代价／权衡
放置约束更强、组合搜索更慢；大模型双权重副本可能连单机都放不下，只能按 segment 对齐而非整实例同机。
D5

KV 采用 pull，而不是 push

把接收端显存从被动淹没改成按需取用。

决策问题
突发流量下，大量 prefill 同时完成，decode 侧显存怎样不被一次性 KV 推送打爆？
被否决方案
由 prefill 主动 push 全部 KV。该方案是论文 §4.3 的直接对照；论文没有把 push 绑定到某个具名 baseline。
为什么这样选
Decode 按需 fetch，prefill 完成后把 KV 留在自己的 GPU HBM，天然形成排队缓冲；两类实例可按各自节奏前进。
代价／权衡
压力并未凭空消失，而是部分转移到 prefill 侧显存与驻留管理；还需处理传输和计算重叠、容量上限与故障恢复。
D6

模拟器搜索 + 周期性重规划

把昂贵的集群试错换成校准过的离散事件模拟。

决策问题
负载长度和到达过程不规则，解析式难以直接给 attainment；真实集群逐个试配置又太慢。
被否决方案
对所有候选做真实 testbed profiling；或只做一次静态规划。相较 AlpaServe 的非自回归统计复用目标，这里还必须模拟自回归 decode 与双 SLO。
为什么这样选
从历史 trace 拟合分布、重采样模拟，二分搜索最大可行速率；负载漂移后按近期历史重跑算法，再重载权重。
代价／权衡
依赖中长期负载可预测和延迟模型准确；短时到达难以预测，重载权重需分钟级，不适合每次小幅波动都迁移。
▶ 跑一遍 · chunked-prefill 的 KV 重读代价

论文 §2.3 给出：一个 prefill 等分为 N 个 chunk 后，历史 KV 读取总量为 N + (N−1) + … + 1，而非 chunk 情形为 N。以下 N = 4 是示例值，把一个 chunk 的 KV 读取量归一化为 1。

  1. 不分块：4 个 chunk 对应的 KV 各读一次，总量 4。
  2. 分 4 块：第 1 块读 4，第 2 块读 3，第 3 块读 2，第 4 块读 1。
  3. chunked 总量 = 4 + 3 + 2 + 1 = 10。
  4. 这个例子的归一化读取量比 = 10 / 4 = 2.5×。

这解释了为什么“缩小 chunk 保护 TPOT”不是免费的：它缓解干扰，同时增加 prefill 执行与显存访问。2.5× 只对应示例 N = 4，不是论文实测加速／减速比。

07 / Critical reading

边界写清楚，结论才真正可复用。

论文已经主动讨论不少限制；剩下的问题集中在负载代表性、缓冲容量和运维失效模式。以下把“论文自认”与“读者质疑”分栏。

论文自认 / §4.3、§7
  • 离线吞吐场景不一定受益。不敏感于延迟时，chunked-prefill + piggyback 可能更能持续填满 batch。
  • 少量 GPU 时设计空间受限。单卡或极小集群难以拆池、调并行与独立扩容，非解耦系统可能更简单。
  • 没有实现 preemption 与 fault tolerance。FCFS 有 convoy effect；P／D 依赖可能传播故障。
  • 重规划依赖负载时间尺度。短时到达不可预测，算法秒级到分钟级、权重重载分钟级，只适合较慢的负载漂移。
  • 长上下文并非单向利好。KV 传输随 prompt 线性增长；论文认为 prefill 二次增长与更强干扰仍让解耦有前景，但这不是长上下文实测结论。
工程师视角 / 读者质疑
  • 负载外推要谨慎。数据无时间戳，实验用 Poisson 到达；真实服务的突发、会话相关性与多峰分布可能改变队列和重规划效果。
  • SLO 是经验设定。Table 1 的预算不是行业统一标准；换一个 attainment 或只收紧其中一个 SLO，最优 placement 可能不同。
  • 硬件与模型覆盖面有限。主体是 OPT、MHA、FP16、A100。论文推断 GQA／MQA 会因 KV 更小而更有利，但该推断不是一组独立实测。
  • pull 只是把洪峰移到上游缓冲。P 侧 HBM 的驻留配额、写满后的行为与 KV 生命周期，是生产化必须补出的容量模型。
  • 故障域需要重新设计。一个 decode instance 对应多个 prefill instance 时，副本级故障不再天然等价于请求级隔离。
可以直接偷的思想
  • 把 SLA 写进目标函数：先算合格请求，再谈吞吐与成本。
  • 按资源 regime 拆执行池：compute-bound 与 bandwidth-bound 不必共享 batch／并行策略。
  • 把状态传输纳入 placement：知道“哪一层的数据流向哪里”，比只看总带宽更有用。
  • 用接收端 pull 将突发变成显式队列，但必须给上游 buffer 设计容量与失效策略。
  • 用少量真实 profiling 校准模拟器，再把搜索、复制与周期重规划自动化。
▶ 跑一遍 · 为什么 175B 的完整 P／D 对放不进 8 卡节点

数值来自 §4.2 与 Table 1：OPT-175B 在 FP16 下权重为 350 GB，单节点 8 × 80 GB A100。

  1. 一个完整 prefill instance 权重：350 GB。
  2. 一个完整 decode instance 还要自己的权重副本：再加 350 GB。
  3. 仅权重合计 = 350 × 2 = 700 GB。
  4. 节点标称显存 = 8 × 80 = 640 GB。
  5. 700 > 640，还没计 KV cache、激活与运行时开销，因此完整 P／D 对无法同机。

这正是“按 inter-op stage 对齐 segment”而非“整实例同机”的必要性：只要求对应层的 P／D segment 同节点，让 KV 仍能走 NVLINK。
